# コンテンツ構造・実装方針・移行設計

作成日: 2026-09-11 / 状態: 実装前の仕様案。以下のパス・型・検証処理は、明記しない限り現時点の実装を示すものではない。

## 1. 技術方針

既存のAstro + TypeScript、静的な数式表示、原稿と生成物の分離は再利用候補とする [01-research.md: R01–03]。学習体験を変えるために、フレームワークを変えること自体を目標にしない。

本文・式・証明・出典は静的に読める形を基本とし、可視化や進捗など必要な部分だけを操作可能にする。初期の利用にログインや独自バックエンドを必須としない。

ただし、現行の「1用語1ページ・2級中心」のデータ構造を、全学習体験の制約にしない。原稿の再利用、コース、到達目標、問題、範囲の版を分離する。

## 2. 正本となるエンティティ

|種類|役割|主要フィールド|
|Lesson|教材の正本。級ごとに複製しない|ID、slug、タイトル、別名、分野、目標、表示層、前提、出典、公開・確認状態|
|Section|教材内の安定した参照先|section ID、種類、表示深度、必要前提、本文、主張ID|
|Objective|理解・使用・解釈・証明などの学習目標|ID、行動を示す文、確認方法、対応する教材・問題|
|Module|分野内の学習単元|ID、中心的な問い、教材の順序、チェックポイント|
|Course|目標別の読む順序|コースID、必要目標、読む節、任意の発展、単元順|
|SyllabusVersion|試験範囲の版|ID、資格区分、適用期間、公式資料、確認日、出典の表記日|
|Alignment|公式範囲と学習目標の対応|範囲版、出典の箇所、目標ID、必要深度、確認状態|
|Question|独自問題と解説|ID、問題版、目標、形式、正答、採点条件、ヒント、誤答理由|
|Misconception|典型的な混同|ID、誤解の説明、判定する問題、復習先の節|
|Lab|操作型教材|ID、問い、操作変数、条件、数値基準、代替説明、関連先|
|Case|応用ケース|ID、問い、データ、設計、方法、結果、限界、演習|
|Reference / Dataset|出典と素材の利用条件|ID、著者・機関、名称、版、節、URL、確認日、権利・入手元|
|Review / Erratum|確認と訂正の履歴|対象ID・版、確認者、方法、結果、影響範囲、訂正内容|

用語索引、公式索引、分布比較、コース目次は、可能な限り正本から生成する。索引のために説明文を別管理して内容がずれる状態を避ける。

## 3. Lessonの仕様例

```yaml
schema_version: 2
id: M07-08
slug: normal-distribution
title: 正規分布
aliases: [ガウス分布, normal distribution, Gaussian distribution]
module_id: M07
status: draft
objectives:
  - normal-interpret-density
  - normal-tail-probability
  - normal-normalization-proof
sections:
  - id: core
    depth: basic
    initially_open: true
    prerequisite_ids: [mean-basic, sd-basic, density-area]
  - id: worked-example
    depth: basic
    initially_open: true
  - id: normalization-proof
    depth: rigorous
    initially_open: false
    prerequisite_ids: [double-integral, polar-change-of-variables]
references: [nist-normal, statlect-normal]
review_status: not_reviewed
```

この例の前提・参照IDは説明用。実装時には全IDの実在性を検証してから使う。現行 `src/content.config.ts` のschemaではなく、次期の論理モデルである。

Lessonは「何を説明するか」、Courseは「どの深さまで読むか」を持つ。例えば同じ正規分布ページの `core` を2級のルートが、`normalization-proof` を任意の数学ルートが参照できる。

## 4. 複数の版を混同しない

管理する版は最低でも次の四つ。

- 教材の内容版: 定義、式、説明、出典を変更した版。
- 問題の版: 問題文・解答・採点条件を変更した版。
- 試験範囲の版: 公式の適用期間を持つ版。
- 進捗データのschema版: 保存形式の変更に対応する版。

試験範囲の年月と記事更新日を一つの `version` に押し込まない。誤植修正だけで既習状態を消さず、理解に影響する修正があったときに対象目標の再確認を促す。

公式資料には、`retrieved_at`、`effective_from`、`effective_to`、`page_version_label`、`document_date_label`、`url`、`source_locator` を分けて持つ。不明な発効日はnull等で保持する。

## 5. 原稿の保管構造案

```text
src/content/
  lessons/             # 次期教材。採用・移行を決めた場合の案
  modules/
  courses/
  cases/
content-data/
  objectives/
  syllabi/
  alignments/
  questions/
  misconceptions/
  labs/
  references/
  datasets/
  reviews/
  migrations/
project-docs/
  learning-platform-design/  # 今回の設計。公開生成物とは別
```

既存の `terms/` をLessonの正本として継続してもよい。重要なのはフォルダ名ではなく、構造と責任を分けること。現行frontmatterに本文全体が入っている部分は、長い証明を扱いやすい本文ブロック等へ移行する選択肢を検討する。段階移行中は読み取りアダプターを置き、新旧原稿を同時に壊さない。

ファイル分割は分野・範囲版・問題セット等を基準とする。一つの巨大JSONにすべてを集めて共同編集や検証を難しくしない。件数による分割の都合で概念のIDを変更しない。

## 6. 画面部品の責任

|部品案|責任|

|PrerequisiteLink|前提を確認し、元の節へ戻れるようにする|
|FormulaCard|式の役割、式、記号、条件を一緒に表示|
|ClaimBlock|定義・定理・モデル仮定・数値結果を識別|
|ProofDisclosure|開閉、直接リンク、必要数学、証明の状態|
|WorkedExample|問題・方法・計算・解釈を順に表示|
|MisconceptionCard|誤解と正しい区別、復習先|
|QuestionRenderer|選択・数値・記述を形式に応じ表示|
|LabFrame|問い・操作・結果・説明・代替表示|
|CourseStepper|選んだコース内の前後と復習先|
|ReferenceNote|主張と資料の該当箇所を結ぶ|

名称は設計上の候補であり、すでに存在するコンポーネント一覧ではない。

## 7. 検索と折りたたみ

- タイトル、別名、日本語・英語、記号、本文、証明、誤解タグを索引対象にする。
- 検索結果は正本ページにまとめ、該当の節へ移動できるようにする。
- 「なぜn−1で割る」「95%は何の確率」のような自然な疑問も別名・問いとして持つ。
- 証明が閉じていても本文は取得可能な構造を基本とし、直接リンクで対象の折りたたみを開く。
- 検索結果で基本説明と発展証明を区別し、初学者が目的と違う深い証明に迷い込むのを減らす。
- URLパラメータによるコース・表示設定で同じ本文の複製ページを量産しない。

## 8. 学習記録

初期版は端末内保存を基本案とする。保存拒否・容量制限・プライベートブラウジングでも本文と演習が利用できるようにする。

記録は、読んだ教材、再開する節、問題への回答、ヒント閲覧、誤解タグ、再確認候補、対応する範囲版に限定する。氏名やメールアドレスを学習の必須条件にしない。

「未着手」「学習中」「基本を確認」「発展を確認」を区別し、閲覧だけで習得を推定しない。確認ルールは公開できる形にし、AIが算出した不透明な合格確率を表示しない。

データのエクスポート・インポート・削除、保存先の説明を用意する。端末内だけにある記録は別端末に自動同期されないことを示す。同期は将来の明示的な追加機能として扱う。

## 9. 可視化・計算の実装契約

計算と描画を分離する。計算関数には入力範囲、出力の意味、数値誤差、境界条件を定める。描画結果だけで正誤を判断しない。

乱数教材はseedと条件を記録し、再現できるようにする。演算量の上限を設け、長い処理で本文や操作を止めない。重い機能の読み込みを遅延させても、説明・条件・静的な図は最初から読めるようにする。

R/Python/Excelの手順は任意の実務補足として扱う。コードを実行できない利用者も、入力・結果・解釈を確認できる。ライブラリ名・関数・バージョンを使用する場合は、制作時点で実際に動かした環境を記録する。

## 10. 既存資産の移行

1. 既存の原稿・URL・タイトル・前提・出典・公開状態を棚卸しする。
2. 307の候補IDに対し、既存活用、改稿、統合、新規、不要の区分を付ける。
3. 最初に少数の代表教材で次期データモデルを検証する。全原稿の一括変換を先に行わない。
4. 統合する記事も、元のURLと主要アンカーから新しい正本への導線を保つ。
5. sourceとschemaを変更する段階で、現行AGENTS.md、生成Skill、キュー、検証スクリプトも整合するよう更新する。新旧の指示を矛盾させたまま量産しない。
6. サイト生成・内部リンク・数式・表示を確認し、生成物を更新する。
7. 変更前へ戻せる単位で移行する。現在の公開物を先に削除しない。

今回の作業は `project-docs/` の設計保存であり、上記の移行を実行したものではない。`docs/` は現在の公開生成物のため、設計原稿の置き場として使わない。

## 11. 自動検証の設計

|検証|失敗させる条件|
|構造|必須ID・目標・前提・出典フィールドがない|
|参照整合性|参照する教材・節・問題・範囲版が存在しない|
|依存関係|必須前提が循環して学習を開始できない|
|公開状態|公開コースが非公開の必須教材・解答へ誘導する|
|範囲対応|未確認の項目を「対応済み」と計上する|
|数式|構文エラー、記号の不整合、式とコードの結果の不一致|
|数値|既知の値・境界・単位・丸めのテストに不一致|
|演習|正答なし・正答の一意性不明・許容誤差未定義・解説なし|
|表示|内部リンク切れ、証明への直接リンク不動作、開閉状態不整合|
|出典・権利|転載素材の利用条件不明、存在未確認の出典|

数学の意味的な正しさはschema検証だけでは判定できない。自動検証が通っても、証明・仮定・問題の独立した確認を省略しない。

## 12. 安全性・プライバシーの最低条件

教材に許可していないスクリプトや任意の埋め込みを入れない。MDX等を採用する場合は信頼する原稿と許可コンポーネントの範囲を明確にする。将来ユーザー入力やデータアップロードを追加する場合は、入力処理と教材描画を分離して検証する。

アクセス解析を追加する場合は、個々の学習内容や誤答を必要なく外部送信しない。まず匿名・集計単位で改善に必要な指標を定義し、公開方針・同意の要否・削除を含めて検討する。
